# Security Policy

Engineering Bridge V1 (1.2.0) is a local supervised bridge that connects an MCP client to local Codex and DSH executors. It is designed for one trusted local operator: treat the MCP client and the workspace configuration as trusted local inputs, and do not expose the process as a remote service. It is not a hardened remote service for untrusted callers.

## Current enforced controls

- The server uses local STDIO and exposes nine tools: `run_task`, `task_result`, `control_task`, `bind_project`, `create_project`, `authorize_workspace_write`, `generate_controlled_patch`, `refine_controlled_patch`, and `apply_controlled_patch`.
- Ordinary `run_task` execution is always read-only, with an optional `executor: "codex" | "dsh"` (default `codex`). Successful interactive turns enter `waiting_for_supervisor_review`; `task_result` exposes state/readiness, bounded evidence, and pre-acceptance `review_output`, then final `output` or `error` after finalization. `control_task` accepts only interactive `run_task` task IDs and state-checks `continue`, `steer`, `interrupt`, and `accept`. Continue preserves native Codex thread continuity; interrupt applies only to running interactive tasks and ends them as failed. DSH has no machine-resumable headless session, so DSH `continue` starts a new execution and no thread id is ever fabricated.
- Workspace IDs and roots come from a startup configuration file. Manual registrations must be absolute and normalized, duplicate IDs are rejected, and MCP callers cannot modify manual registrations. Managed onboarding is confined to configured `project_root` approved roots and requires exact `BIND`/`CREATE` confirmation; canonical real paths are compared, so paths must resolve inside an approved root.
- Managed workspaces are registered read-only by default. `authorize_workspace_write` grants controlled-write permission to a managed workspace only, after exact `AUTHORIZE` confirmation, and never modifies a manual registration.
- Codex runs through `codex app-server --stdio` with approval `never`, a read-only sandbox, OS/shell network disabled, and the configured workspace as its working directory. Instructions use the app-server STDIO protocol; the bridge does not invoke a shell or accept caller-supplied executable paths or process arguments. For Codex `run_task` only, `web_research: true` enables the native live Responses `web_search` model tool while `networkAccess` remains false. This does not grant arbitrary HTTP clients, uploads, POSTs, authenticated browser control, or filesystem writes; DSH fails closed for this option.
- DSH runs through the official headless interface. The bridge pins `DSH_PERMISSION_MODE=read-only` for every DSH process, so a host permission override cannot widen it, and forwards only an explicit environment allowlist (including `DEEPSEEK_API_KEY` and `DSH_TOOLS_MODE`); proxy and other secret-like variables are not forwarded.
- The Codex and DSH children receive small allowlists of inherited environment fields.
- Returned execution failures use fixed error codes and messages rather than forwarding executor stderr or raw internal errors. `partial_output` appears only when a genuine interrupt produced real partial output; the task still ends `failed`, and ordinary failures never re-expose stderr or partial stdout.
- Codex evidence is bounded (string length, changes count, and total entry count). When these existing bounds truncate or evict evidence, explicit markers (`[truncated]`, changes-omitted counts, an evidence-drop item) are returned so the supervisor knows the diagnostic information is incomplete. Markers are not a security guarantee and are not a complete transcript.
- Workspace writes default to disabled. `generate_controlled_patch` and `refine_controlled_patch` are read-only proposal flows available in any registered workspace; they require no write authorization. They verify a clean Git top-level (with an existing HEAD, or unborn-repository support for added-file proposals) and record `base_head`. They never enter supervisor review, expose `review_output`, or accept `control_task` actions.
- After human review outside task state, application requires the completed proposal task, controlled-write permission (managed `AUTHORIZE` or a manual `allow_write: true` entry), and exact `APPLY` confirmation, then rechecks root, HEAD, and clean tracked worktree/index state. It permits modifications to existing tracked regular files and additions of absent ordinary text files only with exact mode 100644 and matching `/dev/null` headers. It rejects deletions, binary patches, mode changes, executable additions, symlinks, submodules, rename/copy, unsafe paths, duplicate paths, and new targets present in HEAD, the index, or the worktree. Fixed no-shell `git apply --check` and `git apply` calls receive the patch on standard input; application is once only and never runs tests, stages, commits, or pushes.
- Two local state files provide restart persistence, written atomically with mode 0600: `<config>.managed-workspaces.json` (the managed workspace catalog) and `<config>.controlled-patches.json` (controlled-patch proposals and applied history). Invalid managed-catalog records are skipped individually; invalid retained controlled-patch records are quarantined without blocking startup, while replay/applied ambiguity and global invariants still fail closed. These files are not a credential store and not a complete audit log.

## Current limitations

The bridge does not authenticate MCP callers. It has no HTTP or remote transport, no automatic timeout, and no persistent task/thread/evidence supervision history: active task supervision state (tasks, threads, evidence, review outputs) is process-local and disappears on restart, even though controlled-patch proposals and the managed workspace catalog persist. Read-only tasks do not verify that configured paths are Git repositories (the controlled-patch flows do). The bridge does not resolve configured manual roots with `realpath` or enforce symlink containment for them; the trusted local operator must therefore control the configuration file, choose workspace roots carefully, and control which local MCP client can start and use the server.

Codex's read-only sandbox and DSH's pinned read-only permission prevent writes, but Engineering Bridge does not provide filesystem read isolation. Executors running as the same operating-system user may still read files outside the configured workspace that the user already has permission to read, so use it only on trusted machines and with trusted local clients.

The read-only execution boundary is an execution control, not a guarantee that prompts or returned text contain no sensitive data. Do not place credentials or secrets in instructions, configuration, or public bug reports.

## Reporting a vulnerability

Do not publish secrets, credentials, private prompts, source code, or personal data in an issue. After the repository is hosted and its security-advisory feature is available, use that feature for private vulnerability reports. Until then, omit sensitive details from public reports.
